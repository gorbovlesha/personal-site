# Агенты разработки и cron

## Процесс

Доска: [Personal site](https://trello.com/b/jWyYTJOD/personal-site). Репозиторий: [gorbovlesha/personal-site](https://github.com/gorbovlesha/personal-site). Точные ARI существующих списков сохранены в `automation/config.json`; колонка `Review / Testing` используется и тестировщиком, и ревьюером.

```text
Backlog ── владелец ──> Ready
Ready ── разработчик ──> In Progress ── PR/результат ──> Review / Testing
                                                       │
                          ошибка тестов или ревью <────┤
                          возврат в In Progress        │
                                                       └─ тесты OK → ревью OK → Done
Done = готово к ручному merge. Слияние выполняет только владелец.
```

Один cron раз в 5 минут выполняет один шаг. Роли запускаются в разных процессах Codex и не делят историю диалога. Одновременно обрабатывается одна карточка; пока она не завершена или не разобрана вручную, следующие не берутся. Порядок Ready определяется позицией карточек. Backlog не трогается.

Разработчик работает в отдельном git worktree и ветке `agents/trello-CARD_ID`. Оркестратор делает коммит и обычный push только этой ветки, создаёт или находит один PR. Если файловых изменений нет, PR не создаётся; содержательный результат остаётся в комментариях. Проверки и финальное ревью пишутся в карточку и PR (когда он есть).

Тестировщик при успехе оставляет карточку в Testing. Ревьюер получает отчёт тестировщика для того же HEAD и BASE. Только успешное финальное ревью переводит в Done. Ошибки тестов/CI или замечания ревью возвращают в In Progress. По умолчанию максимум три попытки разработки; затем требуется вмешательство. Недоступная инфраструктура или отсутствие реального контента — блокер, а не пройденный тест.

## Компоненты и доступы

- `automation/runner.py` — состояние процесса, блокировка, git, GitHub и запуск ролей.
- `automation/prompts/` — инструкции трёх ролей и узкого адаптера Trello.
- Trello работает через подключённый плагин из **реального серверного Codex CLI**. Наличие инструмента в чате не доказывает доступ из cron: проверяется `doctor --online`.
- GitHub операции оркестратора выполняет GitHub CLI (`gh`); для git fetch/push также нужна авторизация. OAuth-сессия плагина не экспортируется в CLI.
- Модель по умолчанию берётся из серверной конфигурации Codex. При необходимости задайте точное имя в поле `model`; роли не выбирают модель сами.

Требуются Linux, Python 3.10+, Git, Node.js 24, bubblewrap (`bwrap`), Codex CLI, GitHub CLI и рабочие серверные авторизации. Для визуальных задач тестировщику нужен доступный браузер: проверяются 360/768/1440 px; без него задача блокируется, зелёный результат не выдумывается. Docker нужен для локальной проверки Caddy при соответствующих задачах; базовый CI проверяет его отдельно.

## Установка на сервер

Запускать от отдельного непривилегированного пользователя, например `codex`. На сервере должен быть постоянный checkout проекта, а не временная рабочая среда чата. Настройте GitHub CLI на сервере через штатный вход:

```bash
gh auth login --hostname github.com --git-protocol https --web
gh auth setup-git
```

Не передавайте токены в карточках, PR или чате. Для строгого разграничения используйте отдельную учётную запись бота с доступом только к этому репозиторию и GitHub ruleset, запрещающий ей обновление `main`. Если подключение имеет права владельца, промпт или локальный код не заменяет серверный запрет GitHub. Не выдавайте процессу production-доступы, sudo или Docker socket без отдельной необходимости.

В checkout должен существовать первый коммит и корректный origin:

```bash
git remote -v
# Если origin ещё не задан:
git remote add origin https://github.com/gorbovlesha/personal-site.git
# Если источник был загружен через плагин, получите историю и используйте чистый clone на сервере.
```

Проверьте доступ из того же окружения, которое использует cron:

```bash
python3 automation/runner.py doctor
python3 automation/runner.py doctor --online
python3 scripts/project.py check --require-node
python3 scripts/project.py test
python3 scripts/project.py build --require-node
```

`doctor --online` читает подключения, не берёт карточки и ничего не пишет в Trello/GitHub. При отсутствии git/gh/Node, первого коммита, origin или авторизации установка не продолжается. После успешного preflight:

```bash
python3 automation/install-cron.py
```

Установщик добавляет только свой помеченный блок в пользовательский crontab; остальные задачи сохраняются. Он не запускает разработку немедленно. Настройка выполняется повторно без дублирования cron-записи. Установка cron требует реального доступа к crontab; в изолированной среде приложения он может быть запрещён. Файл установщика сам по себе не означает, что cron установлен.

## Наблюдение и остановка

```bash
python3 automation/runner.py status
python3 automation/runner.py tick
python3 automation/runner.py pause
python3 automation/install-cron.py --remove
```

`pause` запрещает **следующие** запуски. Он не обрывает выполняющуюся роль и не ждёт освобождения её блокировки. Для экстренной остановки остановите процесс целиком, затем выполните сверку как после сбоя.

Приватное состояние в `.local/automation/` исключено из Git: `state.json`, `pipeline.lock`, `runs/*/agent.log`, структурированные результаты, последние логи проверок, `completed/*.json`, worktrees и cron.log. Файлы создаются с закрытыми правами. Логи могут содержать текст карточек и кода; не публикуйте их. Настройте ротацию и резервное копирование отдельно; старые worktrees не удаляются автоматически, чтобы не потерять незавершённую работу.

## Защита переходов и сбоев

- Один файловый lock охватывает весь шаг, включая внешние операции. Это защита **одного сервера**; запускать второй экземпляр с другим диском нельзя без распределённой блокировки.
- Перед эффектами записывается `pending`. При таймауте, аварии или неясном результате процесс останавливается. Автоматического повторения неизвестной операции нет.
- Перемещение карточки проверяется чтением до и после. Если человек увёл карточку в другой список, агент останавливается.
- Комментарии имеют стабильные маркеры. Гарантии exactly-once при сетевом сбое нет; неоднозначный результат сверяется вручную.
- CI должен успешно завершиться для текущего HEAD; pending не означает success. После изменения HEAD или BASE прежний QA недействителен.
- Обязательные проверки проекта выполняются через bubblewrap: отдельные network/PID namespaces, пустая HOME, без домашней папки сервера и его credentials. Если изоляция недоступна, обхода через обычный subprocess нет.
- Worker-процессы не получают service-токены через env, запускаются с workspace-write без сетевого доступа shell и отключёнными Apps. Trello-адаптер работает read-only по файловой системе; GitHub ему отключён.
- Worker не коммитит, не пушит и не вызывает внешние приложения. Изменения доверенной инфраструктуры, HEAD и отслеживаемого кода тестировщиком/ревьюером блокируют переход.
- В GitHub-адаптере нет операций merge, auto-merge, деплоя или изменения main. Защиту от произвольного кода на уровне всей машины обеспечивает изоляция ОС и серверные права, а не только эти проверки. Авторизация Codex CLI остаётся доступна самому Codex; очистка env не изолирует домашнюю папку пользователя.

После неоднозначного сбоя сначала изучите `state.json`, карточку, PR, удалённую ветку и рабочую копию. Не удаляйте `pending` и не запускайте новую ветку вслепую. Восстановите список карточки и согласованный checkout, затем явно подтвердите сверку:

```bash
python3 automation/runner.py recover --stage developer --confirm-reconciled
# Либо повторить QA на уже опубликованном PR:
python3 automation/runner.py recover --stage tester --confirm-reconciled
```

Команда повторно читает карточку, а для QA проверяет актуальный PR, чистую рабочую копию и наличие текущего base в истории ветки. Если main изменился, сначала вручную интегрируйте его в feature-ветку и обновите PR. Повторное ревью без QA для нового SHA не разрешается. Восстановление задачи без PR или после неоднозначного финального Done требует отдельного ручного разбора; инструмент не угадывает правильное действие.

## Что не автоматизировано

Merge, публикация сайта, изменение прав доступа, согласование личных данных, исправление окружения, ротация секретов и аварийное восстановление. CI и комментарии агентов не заменяют решение владельца о слиянии.
